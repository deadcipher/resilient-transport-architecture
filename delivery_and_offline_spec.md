# Delivery Model, Pending Queue & Backlog Sync Specification

Данный документ описывает правила подтверждения доставки на сетевом уровне, логику работы локальной очереди неотправленных сообщений (`PendingQueue`), дедупликацию и синхронизацию после выхода из оффлайна.

---

## 1. Пайплайн состояний жизненного цикла сообщения

Каждое сообщение проходит 4 сетевых статуса:

```
[Local Draft] ──(1. Send)──> [Queued Locally] ──(2. Socket Push / REST)──> [Accepted by Server] ──(3. Server Push to Recipient)──> [Delivered to Device] ──(4. User Read)──> [Read]
```

1. **`queued_locally`:** Сообщение находится в локальной памяти/базе клиента в ожидании отправки.
2. **`accepted_by_server`:** Сервер принял сообщение, записал в свою БД и вернул клиенту `ack_event` со статусом `accepted`.
3. **`delivered`:** Получатель (устройство получателя) получил сообщение через WS и выслал обратно `ack_event` со статусом `delivered`.
4. **`read`:** Получатель открыл чат/экран с сообщением, генерируя `read_event`.

---

## 2. Локальная очередь оффлайн-отправки (PendingQueue)

Если клиент находится в состоянии `OFFLINE`, `DISCONNECTED` или `RECONNECTING`, отправка через сокет невозможна.

### Логика работы PendingQueue:
1. Сообщение оборачивается в `WireEnvelope` с уникальным `client_request_id` (UUIDv4).
2. Сообщение добавляется в очередь `PendingQueue` (персистентное локальное хранилище).
3. При переходе клиента в состояние `CONNECTED` или `SYNCING_BACKLOG` запускается процесс **Flush Queue**:
   - Из очереди по порядку отправляются все накопившиеся `WireEnvelope`.
   - Если сервер подтверждает прием (`ack_event: accepted`), сообщение удаляется из `PendingQueue`.
   - Если происходит разрыв соединения во время flush, неотправленные/неподтвержденные сообщения остаются в очереди и будут повторно отправлены при следующем подключении.

---

## 3. Дедупликация и Идемпотентность (Deduplication)

При повторных попытках отправки после обрыва связи сервер может получить сообщение, которое он уже успел сохранить.

- **Idempotency Key:** В роли ключа идемпотентности выступает `client_request_id`.
- **Окно дедупликации:** Сервер хранит таблицу последних `client_request_id` за 7 дней.
- **Поведение сервера при дубле:** Если сервер получает `WireEnvelope` с уже существующим `client_request_id`, он **не создает новое сообщение**, а повторно возвращает успешный `ack_event` со статусом `accepted` и оригинальным `message_id`.

---

## 4. Синхронизация бэклога (Backlog Retrieval)

Если клиент находился в оффлайне длительное время (например, несколько часов/дней), при подключении выполняется процедура Catch-up / Sync:

1. В `client_hello` клиент передает свой `last_received_event_id` и `last_received_timestamp`.
2. Если `has_unfetched_backlog: true` в `server_hello`, клиент запрашивает пакет бэклога через REST: `GET /api/v1/sync/backlog?since_event_id=...&limit=100`.
3. Сервер отдаёт массив пропущенных `WireEnvelope` до тех пор, пока клиент полностью не выйдет на текущую метку времени (`steady state`).
